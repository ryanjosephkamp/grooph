# Handoff 0005 · Templates and the pattern library

**Stage:** 4 · **Implementer:** Opus 5 · **Effort:** `high` (floor `high`) · **Branch:** `slice/0005-templates` · **Drafted:** 2026-09-18 · **Confirmed by owner:** pending

## Objective

Make workflows reusable by name. An agent (or the owner) says "use the review-gate template" and gets a validated graph with the blanks named; a graph or part of one can be saved as a template; the sixteen patterns from spec §10 exist as real, validated documents; and the library is published with the site so anyone can fetch a template without cloning. This is the vocabulary the executive skill (slice 0006) recommends from. No web UI work in this slice.

## Success criteria

1. **Green from a fresh clone.** `pnpm install --frozen-lockfile && pnpm -r build && pnpm -r test` and `pnpm --filter @grooph/web test:e2e` exit 0; CI green.
2. **The template block** of `docs/templates.md` §1 is in the types, schema, canonical order (after `lineage`), and JSON Schema. `E_IS_TEMPLATE` and `E_UNFILLED_SLOT` are implemented as graph-ir §3 describes, each with a failing fixture.
3. **Core operations** of `docs/templates.md` §2 (`instantiate`, `insertFragment`, `extractTemplate`, `templateIndexEntry`, `findSlots`) are pure, exported from `@grooph/core`, and tested, including: instantiate then extract round-trips meaning; `insertFragment` re-derives colliding ids and returns the id map; a fragment's loops and scoped policies come along only when fully inside.
4. **Registries and CLI** per `docs/templates.md` §3–4: project, user, built-in and remote resolution in that order; `grooph template list | show | use | insert | save | add`. Built-in patterns are bundled at build time (core stays free of file and network access; the CLI does the I/O). Remote fetch is used only when a name is not found locally or on `add`, fails with a clear message offline, and is tested against a local static server, not the live site.
5. **The pattern library.** All sixteen documents of `docs/templates.md` §5 exist under `patterns/`, follow every rule in that section, and a test instantiates each with its slot examples and validates it for export: no errors, warnings exactly as its sidecar lists. `patterns/index.json` is generated by a script, committed, and CI fails when it is stale. `patterns/README.md` lists the patterns with their when-to-use lines, generated from the same data.
6. **Published.** `deploy.yml` publishes `patterns/` beside the app so `https://ryanjosephkamp.github.io/grooph/patterns/index.json` and each pattern file resolve after merge; verified on the branch by serving the built site locally under `/grooph/`.
7. **Carried from review 0004.** `E_IRREVERSIBLE_NO_GATE` follows the new graph-ir wording (every way in passes a human; no inbound edge means ungated) with a second failing fixture for the mixed-inbound case. Lead-brief §9 says a `patch` is preferably a grooph op list and distinguishes a kickoff amendment from an up-front redesign (graph-ir §2). Goldens regenerated and read as documents.
8. **Dogfood by CLI only, no model spend.** A transcript in the handback: `grooph template use review-gate …` → `grooph apply` one small change → `grooph validate --for-export` → `grooph export`, plus `grooph template save` of a fragment from that graph and `grooph template insert` of `human-gated-irreversible` into another.

## Spec constraints that apply here

- §10: patterns are named shapes with a when-to-use, not slogans. Gauntlet-style polish is one bounded entry (`taste-polish`), never a default.
- §13: no swarm on coupled concerns; evidence quality is gated; zero-to-one work prefers `spec-then-loop`; loops carry budget brakes.
- §4.7: every pattern stays well under the `W_DOC_TOO_LARGE` budget; a pattern that needs long briefs is over-specified.
- graph-ir §2 Latitude and A-009: briefs are purpose, limits, outputs.
- Decision 0005: core has no runtime dependencies and no I/O.
