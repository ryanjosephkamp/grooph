## The sentence proposed for the privacy page

`docs/privacy.md` is the owner's to word. Proposed, after the item "The event hook":

> **Installed outside the project** (`grooph hooks install --user`), the hook writes the same lines and nothing more, to a folder of its own in your home: `~/.grooph/events/`, one folder for each project folder you have listed with `grooph hooks watch`, named after that folder. It records only a session working in a listed folder; for every other session on the machine it writes nothing. The list itself, `~/.grooph/watched.json`, holds the paths of the folders you listed. That folder, the list and the session files are made readable by your account alone. None of it leaves the machine: `grooph events push` sends a project's own `.grooph/events/` and nothing else.

## Decisions made

- **The home folder is `GROOPH_HOME`**, which `registry.ts` already reads for the user's templates. The driver agreed.
- **The mode by an argument, the home from where the hook's file was installed.** The entry ends in `--user`; the hook takes grooph's folder to be the one its file is in, which is what `GROOPH_HOME` named when `install` ran, carried in the entry as the hook's whole path. It reads no variable for it. Reason: a session started without the variable would otherwise send one install's lines into another folder's record, and a test that forgot it would read the real `~/.grooph`. The driver agreed. The commands read `GROOPH_HOME` as decided.
- **The name of a folder's record**: its own name, and eight characters of the sha256 of its whole path (longer if a listed folder already has that name). Readable; two projects with one name do not share a record; a folder listed again finds the record it left. The name is kept in the list, so the hook computes nothing.
- **A folder is listed with no link in its path and in the letters it is really named in** (`realpath`, the system's own), and the hook compares a session's folder the same way: on this disk a path typed in other letters is the same folder.
- **The folder a session was started in is asked before the folder it is working in**, so one session's lines stay in one record. The innermost listed folder wins.
- **A person's settings are edited in the text**, grooph's own entries only, and never read into an object and written out again. Written after the first reader showed what a rewrite does (`1e400` to `null`, a key written twice, the layout). The result is parsed and held to what was meant before it is written.
- **A file is written beside itself and renamed, and in no other way.** Where that cannot be done (read-only, a second name, a folder that takes no new file) the command refuses. The first reader emptied a settings file by killing the in-place write that used to be the fallback.
- **An entry is grooph's only if it is exactly what `install --user` writes**, whatever folder its path names (so `remove --user` finds entries from an install made under another `GROOPH_HOME`, as the driver asked). Everything else that names the hook is left, counted, and keeps the hook's file from being removed under it.
- **With both an install in the project and a listing, the record outside the project is the one read**, by session: of a session the record holds, the project's own folder adds only what the session said (a plan, a note). Reason: it is the record a session in the project cannot write, and the one still added to after a project install is removed and its files left. The first build did the reverse, by file name, and both readers walked through it.
- **`status` prints the project's lines as before and, where anything of the user-level install exists, a block under them.** A machine with no such install sees no new line.
- **The record is the person's alone** (0700, 0600; the list 0600): it holds the folder paths and session times of every listed project.
- **What cannot be listed**: a folder that holds grooph's own folder or is in it, and a person's whole home folder (the owner chose A, not B).
- **`grooph hooks watch` takes several folders**, and the commands that change grooph's folder take turns by a lock that names its holder: taken at once from a process that is gone, never from one that is there.
- **grooph's folder keeps a note of the settings files an install was made into** (`installed.json`), so that `remove --user` for one account's settings keeps the hook's file while another account's still names it. `CLAUDE_CONFIG_DIR` names one settings folder at a time, and this Mac has more than one.
- **`sessions --json` says where it read on standard error**, so the data is the data.

## Deviations

- **`GROOPH_EVENTS_DIR` does not "keep its meaning" outside the project.** The handoff says it does. With `--user` the hook does not read it; for an install in a project it means what it did, to the byte. The first reader showed what obeying it did (a folder made inside the watched project, two projects' sessions in one folder, open folders, events no reader finds), and it would be the one place a hook that runs outside the sandbox takes where it writes from something a session's environment can set. Asked of the driver, who agreed ("build it") and asked for the status line, the sentence in `docs/subagents.md` and the four tests, which are in.
- **A project's `install` is refused in one folder where `main` allowed it**: a folder whose settings file is the harness's own user-level one (a home folder with the defaults; `CLAUDE_CONFIG_DIR` and `CODEX_HOME` are honored in working that out). What a real project gets is still `main`'s, byte for byte. Told to the driver, who agreed.
- **A sentence outside the allowed changes is now untrue, and is left for the driver**: `docs/HANDBACK-operator.md` line 144 says the hook is "under two hundred lines". It is 252. The driver has said it is theirs to change at the release.

## Risks and leftovers

What was not tried:

- **No harness has run a user-level entry of grooph's.** The hook was run by tests and by hand as a harness runs it, and the entry by `sh`, `bash` and `zsh`. Whether Claude Code and Codex fire it, whether Codex needs the session's folder trusted for a user-level hook, whether either closes a hook's input, and whether a project's settings `env` reaches a user-level hook: all for slice 0111 or the owner's first install.
- **Whether a session notices a recorder installed this way.** Nothing here says it does not. That is slice 0111's arm.
- Windows, Linux, a disk that tells letters' cases apart, a network volume, Node 18.

What a reader showed and is left as it is, each said in `docs/subagents.md`:

- A second name (hard link) for a file that begins as an events file does, or for an empty file, put on and taken off in a loop while hooks fire, is reached a few times in a thousand, in both layouts. Outside the project a session that can write only in its project cannot make one there.
- An install followed by a remove does not give back: a `hooks` that was there and empty, an event's list that was there and empty, and the space inside an empty object.
- `remove --user` refuses a settings file it could not put back whole. It keeps the hook's file, so nothing errors, and says why.
- A command stopped part way can leave a `….grooph-tmp` file (0 to 4 in each 200 kills); nothing reads, clears or mentions them.
- A session working in a folder reached through a link is recorded under the folder the link leads to; a session with no start folder (Codex) whose working folder moves between listed folders leaves lines in both; a listed folder renamed is no longer listed; a new folder at a listed folder's old path takes up its record.
- A session can still put a file in its project's `.grooph/events/` under a new session id (or a recorded id with another harness's name) and have it shown as a session of that project, and can add a plan or a note to a real one. A note counts as the session being heard from, so one written under a recorded session's id makes a session that had gone quiet read as working, and its unfinished subagents as running. All as in a project install; the last is how `packages/core` reads a note.
- A command killed while it waits for or takes the lock can leave a file named `grooph.lock.<process>.<token>` beside it (2 after 150 kills); nothing reads or clears them. A lock that names a process that is there and is not grooph holds every command off for its ten seconds until the lock is removed by hand, as the message says.
- A project's `remove` in a home folder writes that settings file the old way (read and written out whole).

Reasoned, not run: extended attributes and access lists are not carried to a rewritten settings file; a change the harness makes to its settings in the same moment as an install could be lost; a lock held by a process whose number the system gives to another process keeps commands waiting their ten seconds until someone removes it; a value nested 6,000 deep in settings is refused with the system's own words.

Not this slice's, and seen:

- `grooph mcp` writes `said-<session>.jsonl` into the project, and its `grooph_running` tool reads the project's own events only. With a user-level install a watched project still gets that one file if a session uses those tools.
- A field of a hook's line has no limit on its length (the first reader made a 6 MB line with a subagent's type, and that session then fell out of `grooph sessions`, which reads a file's last 4 MB). In both layouts, and a question about what a line may hold (A-012 to A-017).
- The readers follow a link among a project's own event files, and a project install's reader can be shown another folder's sessions through a link at `.grooph/events`. Pipes are no longer read anywhere.
- `grooph hooks install` in a project still copies the hook with a plain copy, so a hook started in that instant could meet half a file. The user-level install writes it whole.
- `experiments/game/setup/starting-contents.claude-code.sha256` pins the hook's bytes: once this is on `main`, that experiment's `make-repo.sh` stops at its manifest, as the handoff expects.

For slice 0111 to try: whether a user-level entry fires in Claude Code under a clean profile (`CLAUDE_CONFIG_DIR` and `GROOPH_HOME` named at install; the hook then needs neither at run time); whether a session shows any sign of the recorder (its folder listing and `git status` hold nothing; the settings entry is in the profile, which a session may read); what a session's `/hooks` or its transcript says of a user-level hook; whether Codex runs one without the folder's trust; and what the hook costs a real session at a turn's end, where it is waited for.
