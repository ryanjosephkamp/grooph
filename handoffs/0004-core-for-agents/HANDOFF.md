# Handoff 0004 · Core for agents

**Stage:** 3 · **Implementer:** Opus 5 · **Effort:** `high` (floor `high`) · **Branch:** `slice/0004-core-for-agents` · **Drafted:** 2026-09-18 · **Confirmed by owner:** 2026-09-18 (two acceptance runs approved)

## Objective

Agents will build most graphs (decision 0007), so the core has to be complete and the vocabulary for changing a document has to live where every shell can reach it. This slice moves the typed document operations from the web app into `packages/core`, brings the document up to the current `docs/graph-ir.md` (the alignments decided in reviews 0001 and 0002, the full rule catalog, and the new `adaptation` field), teaches the Claude Code compiler about adaptation and the working copy, gives the CLI `new` and `apply`, and proves the result with one real headless run.

## Success criteria

1. **Green from a fresh clone.** `pnpm install --frozen-lockfile && pnpm -r build && pnpm -r test` and `pnpm --filter @grooph/web test:e2e` exit 0; CI green on the branch.
2. **Operations live in core.** Everything in `apps/web/src/doc/ops.ts` (and the pure helpers it needs, such as id derivation) is exported from `@grooph/core` with its tests; the web app imports them from core and keeps no copy. An `applyOps(doc, ops[])` entry point takes a JSON-serialisable list of `{ op, ...args }` and returns the new document or a precise error naming the failing op, so the CLI today and the MCP server later share one format. The op names and argument shapes are documented in `packages/core/README.md`.
3. **Document alignments.** Canonical key order puts `kind` second on every node (graph-ir §7); the graph's own id is in the `E_DUPLICATE_ID` set; `write-outputs` is a known capability mapped per `docs/targets/claude-code.md`, and the agent body states the "only the files you declare in outputs" rule; fixtures are stored in canonical form; the review-loop fixture's critic allows `write-outputs`. The golden package is regenerated by the existing script and reviewed by you as a document before committing.
4. **Every rule in graph-ir §3 is implemented** with its exact code, table-order output, and at least one failing fixture that reports that code: `E_CRITIC_NOT_ISOLATED`, `E_OWNERSHIP_CONFLICT`, `E_IRREVERSIBLE_NO_GATE`, `W_HOMOGENEOUS_CRITICS`, `W_FANOUT_ON_COUPLED`, `W_LONG_LOOP_NO_BUDGET`, `W_ASPIRATION_AS_ACCEPTANCE`, `W_ONLY_MAX_ITERATIONS`, `W_UNREACHABLE_NODE`, `W_NO_TERMINAL`, `W_OUTPUT_NOT_WRITABLE`, `W_UNKNOWN_KEY`, in addition to the ten from slice 0001. `PLANNED_CODES` is empty. Valid fixtures may carry expected warnings, listed in a sidecar the fixture walk checks exactly (the review-loop graph will report `W_HOMOGENEOUS_CRITICS`; that is a true statement about it and it stays).
5. **Adaptation.** `adaptation` is in the types, schema and canonical order with default `adaptive` applied at compile time (the document is not rewritten to add it). `RunNote.amendment` exists. The compiler emits lead-brief section 9 "Adapting the graph" for each of the three levels exactly as `docs/targets/claude-code.md` and graph-ir §2 describe, including the brakes list verbatim and the mid-run-node rule; run setup copies the source document into the run folder as the working copy. Golden packages exist for the review loop at `adaptive` (the default) and one small graph at `fixed`, so both texts are reviewable.
6. **CLI.** `grooph new --name <n> [--goal <g>] [--target <h>] [--out <file>]` writes a minimal canonical document; `grooph apply <file> --ops <ops.json | -> [--write]` applies an op list through `applyOps`, prints the resulting issues, and exits 1 without writing when an op fails. `grooph validate` accepts a run's working copy like any other document.
7. **Web app follows.** The capability picker offers `write-outputs`; the Graph panel has an adaptation control with a one-line explanation of each level; new rule codes appear in the panel with highlighting with no per-code UI work. No other web feature work.
8. **One real run.** `scripts/e2e-claude-code.sh` is updated for the regenerated package and run at most twice (owner-approved). It passes when: the critic wrote `REVIEW.md` itself (the lead did not file it); the working copy exists in the run folder; the run ended through a stop, the stop node, or a halt at the gate. To exercise adaptation honestly, the scratch task includes one requirement the graph does not cover (for example, the checklist asks for a short usage note in `README.md`, which the builder's `owns` does not include); report what the lead did about it: amended the working copy with a note, handled it inside an existing node, or ignored it. Any of these is a finding, not a failure; fabricating an amendment note without changing the working copy, or loosening a brake, is a failure.
