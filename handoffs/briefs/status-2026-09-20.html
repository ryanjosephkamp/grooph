What grooph can do today

grooph is an authoring and compilation tool for multi-agent loop graphs. A graph document (JSON, with a published schema) describes agents, edges, loops, stops and human gates; a validator enforces loop hygiene with 24 coded rules; a compiler emits a prompt package that a Claude Code session runs as the lead. grooph never calls a model itself.

  • Sixteen built-in templates, each a validated graph document, browsable in the app and installable by name from the published index. Every one now has a proving record linked from its page.
  • A CLI (grooph): validate, compile, apply typed operations, use and insert templates, share a proposal set, list and bundle runs, adopt a run's amended working copy, and watch a run live on the phone.
  • A local-first web app on GitHub Pages: canvas editing on a phone, template library, compare view for candidate graphs, and a run view that lights the graph from the run's notes, including the stop that fired.
  • The design skill (/grooph-design): from a Claude Code session, describe a project and get one to three validated candidate graphs and a phone link to compare them. The driver has used it end to end once (slice 0007's workflow); you have not used it yourself yet.
  • The proving runner: builds a scratch project from a task, instantiates a template, runs the package headless under a spend ledger and a narrow permission allowlist, copies the evidence into the repo, and asserts on it.

Live: the app · template index · spend ledger. Source of "what works": docs/PROGRESS.md § Now.

The experiments: what a proving run is and what it records

A proving run answers one question per template: does a real Claude Code session, given only the package grooph emits, run the graph as designed and end through one of its stops? Each run is one data point about grooph's output. It is not a benchmark of the template against anything else.

How one run goes. The runner copies a small Node project from experiments/patterns/<id>/task/ into a scratch folder, instantiates the template with that task's slot values, exports the package, and starts claude -p headless with a permission allowlist passed by flag, a per-run dollar ceiling, and no MCP servers. When the session ends, the runner copies the evidence into the repository and runs its assertions.

Findings

  • The package works as a runtime contract. Eighteen proving sessions and three earlier acceptance runs followed the graph: dispatched the named agents as their own subagents, kept critics isolated, evaluated stops in order, and wrote the notes the run view reads. The first batch's seven defects were all in wording the lead brief emitted, and the re-proof showed the fixes landing.
  • A loop only loops when the critic knows something the builder does not. Zero back edges in the first seven runs; four in the eleven where tasks used held-out cases, a held-out reference, or a phase checklist. Two designs still did not force a loop: a frontier red team could not break a strong builder given a complete contract, and a fast builder passed all 43 held-out phase-2 cases first try. Those are recorded as lost bets, not failures.
  • Gates hold. Every human gate in headless mode ended the run with a halt note first and nothing irreversible done; the irreversible fragment left its publish file absent.
  • Dispatch counting is a real brake. Leads kept an exact dispatch count in seven of eight loops that had one; the eighth (the four-critic bank) counted 8 a round for 6, and the check caught it.
  • Adaptive runs amend within the rules. The first adaptive run added a file to a builder's ownership before dispatching; the retrospective template produced five proposals and zero amendments, as its level requires. One amendment exposed a gap: a capability change cannot reach the compiled agent file, so the lead used a stand-in. That is slice 0012's first fix.
  • Harness quirks worth knowing. Claude Code misreports turns and duration when subagents run in parallel; a headless lead can see its dollar ceiling and may halt on it; compound shell commands are refused under a narrow allowlist (the kickoff now says to run commands bare, and those refusals stopped).

Effectiveness, speed and cost: what we know and what we do not

Effectiveness against alternatives: unknown

There is no run of the same task without a graph, with a plain single-agent session, or with another orchestration approach. Nothing in the repository supports a claim that a loop graph produces better, worse or equal work. The proving ground measures whether grooph's output drives a session as designed, which is a precondition for that question, not an answer to it. The comparison is stage 10 (paired runs, one harness against another and a graph against no graph), which is deferred until Codex is available. It could be brought forward for Claude Code alone at about $2 to $6 a pair if you want that evidence sooner.

Speed: measured, not compared

The sixteen current runs took from 1m26s (a grind loop, one round) to 15m58s (four critics in parallel, two rounds), median about 5m40s. That is the time for a small Node task to be built, judged and, in four cases, revised. No baseline exists for the same tasks done another way, so nothing here says grooph is faster or slower.

Cost: measured well

Per run, $0.66 to $5.76, median about $1.94; the cost of a round rises with the number of agents dispatched (the bank runs six agents a round, about $2.80). Total proving spend $39.58 of a $45.00 cap over 23 invocations, all in the ledger. These figures are what Claude Code reports as the API-rate cost of the tokens; under the subscription sign-in this Mac uses they draw on your plan's usage rather than being billed. What is not measured: the cost of the driver and implementer sessions that build grooph itself, which are ordinary interactive sessions outside any ledger.

Known risks and what is not proved

  • Every run is one data point on one small task with one harness version (Claude Code 2.1.268 to 2.1.278) and one lead model (Opus 5). Larger graphs, bigger codebases and other models are untested.
  • Held-out evidence is protected by instruction only. In the three runs that used it no builder read it, and the transcript digest would show if one had.
  • Real-finger phone interaction is tested by browser emulation only, plus your own phone session on 09-18.
  • Dollar and turn budgets are advisory inside a session; only dispatch counts and minutes are exact brakes.
