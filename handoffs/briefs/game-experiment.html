The game

A shooter in a small open arena that you can play in first person or in third, switching whenever you like. You stand in a walled valley of ruins and rock under an open sky, with a rifle. Enemies come in waves. Clear every wave and the round is won; fall to zero health and it is lost. Then you play again.

Your words were "first-person + third-person (player can switch between views) in a small open shooter arena world". The spec keeps that and sizes it for one afternoon.

Fixed for both builds:

  • A browser, three.js, npm install && npm run dev, static files in dist/, no backend.
  • No asset is downloaded from anywhere. Every model, texture and sound is made by code in the repository, so a public repository's license is clean.
  • A small read-only surface, window.__game, and two flags (?seed=, ?test=1) so that a script can play it. The checks rest on it.

Seven milestones

A game you can walk in, shoot in, win and lose exists by about hour two. Everything after makes it better. At the end of every milestone the game is playable.

ByAt its end a player can
M0 · A page0:20open the page and see lit ground under a sky and a menu
M1 · Walk1:00start a round, walk, sprint, jump, look; walls stop them
M2 · Shoot, win, lose2:00fire and reload; enemies come, take hits, fall and hurt; win or lose; play again
M3 · Two views2:45press V and play in third person, and back; shots land where the crosshair points in both
M4 · A place3:45fight in an arena worth looking at: cover, high ground, ruins, light; three waves; pickups
M5 · Feel4:45hear it and feel a hit: generated sound, hit markers, enemies that flinch, a pause screen
M6 · Depth5:30meet shooters, pick a second weapon, face a heavy enemy, keep a best score, change settings

If six hours proves short, the spec says what to drop, from the end: settings and the best score, the heavy enemy, the second weapon, shooters, walking animation, pickups, shadows. Never anything in M0 to M3, and never the test surface.

The graph both sessions run

One session: a lead and its subagents. It validates with no error and no warning, and grooph export writes a Claude Code package from it.

Drawn by grooph image from experiments/game/arena.grooph.json. Purple is the loop over one milestone; teal is the loop over the list.

  • A person at the two ends, and nobody between. You start the clock and you read the result. No stop in the graph halts the run: each leads on, to the next milestone or to the wrap-up.
  • One milestone a round. A builder builds it on top of what is there. One check builds the game; a second re-runs what earlier milestones left behind.
  • A critic that plays. Fresh each time, it has not seen how the game was built. It plays the build in a headless browser and takes pictures. On a pass it writes what it just did as a check, so the next milestone cannot quietly undo it.
  • The end is tidy. When the list is done or the clock says so, the repository is brought to its last playable state, and a second fresh critic plays the whole of it for you to read.

The checks no builder sees

Twenty-six things a player can do. Twenty-one a script can tell; five are yours, in ten minutes with each build, not knowing which is which.

21 of 21 passagainst a stand-in page that has the game's test surface and works.

21 of 21 failagainst the same page with every behavior turned off.

Then each behavior was turned off alone, and the check that looks for it failed for its own reason. A check that passes against nothing is not a check, so this was done before any game exists.

How a run is kept from them. They live in grooph's repository and never in a game's. Nothing a session is given names them. Each game is cloned outside grooph's clone, the session's permissions stop at its own folder, and it starts from a clean profile: none of your account's instructions, skills, servers or session tools. After the run the transcript is searched for the folder's name; a hit is reported.

What keeps it fair

  • The same spec, byte for byte, and the same graph, compiled once for each harness.
  • The same machine, one run at a time, and the same starting contents in each repository: a license, the spec, the package, three lines of README.
  • The same clock. Up to six hours from your "start". A wall at 6 h 15 min. The result is the last commit that plays, not whatever was half done when the clock stopped. A run that ticks all seven milestones early ends early.
  • Your answers, fixed now: "start" and "close". If a session asks in the middle it gets one line, the same in both: "Go on as the lead brief says. Nobody is here until the end."
  • The same extension, if there is one: decided once for both, after both are scored and you have played both. The six-hour results are recorded first and stay.
  • Everything is recorded before a result is used: the run folder, when each subagent started and stopped, what each harness says it cost, every commit with its time.
  • A check that turns out to be wrong is corrected for both builds or for neither, and both sets of results are reported.

What it can show, and what it cannot

It can show

What happened, once, in each harness: how many milestones each run's own critic ticked, what a player can do in each build by the same checks and the same ten minutes, what each cost, and whether the brakes held for six hours with nobody there.

It cannot show

Which harness is better: one run each, with different models, on different days. Nor that a loop graph beats a prompt: no session here is given a prompt in its place.

To compare harnesses would take three runs or more in each, in alternating order, scored blind. To say anything about graphs against prompts would take the four arms of the comparison protocol on this task, twice each: eight six-hour runs or more. This is written before the runs so the result cannot move it.

What was not checked

  • No game exists. The checks have only met stand-in pages. A real three.js game may trip a check for a reason the stand-ins could not show. The rehearsal's build would be the first real page they meet, and the protocol says what happens if a check is then found wrong.
  • Six hours and seven milestones are a judgment, not a measurement. Nothing this size has been run from a grooph package: the longest run in the pattern and comparison write-ups took about sixteen minutes.
  • The Codex half does not exist yet. The graph exports for Claude Code today. Whether the same document exports for Codex unchanged is slice 0076's to show.
  • The frame rate check needs a browser with a window on the graphics card for a real game. Against the stand-ins it ran without one.
