What grooph can do today

Version 0.3.0. Live at ryanjosephkamp.github.io/grooph.

  • A graph document. One small JSON file: agents, checks, human gates, stops, edges, and loops with their stops. A person or a model can read and rewrite it in one pass.
  • A validator. 35 rules, 24 for graphs and 11 for maps, each with a code, a document that fires it and one that does not. Every loop must be able to end; a critic must see something the builder did not; an irreversible step needs a person before it.
  • A compiler for one harness, Claude Code: a lead brief, a subagent per agent node, a skill that starts the run, and the notes a run writes.
  • Twenty templates, each with one recorded run. Three seed graphs for research work in the community folder.
  • A CLI: new, template, apply, pick, validate, explain, shape, export, adopt, image, outline, page, glyph, mermaid, watch, runs, hooks, sessions, events, mcp, share, embed.
  • An app that installs and works offline: a front page, your library, an editor for phone and desktop, the templates, a viewer for links, a compare view for proposals, a run view with replay, live sessions, and the operation map.
  • Things to keep and share: pictures as SVG and PNG, an outline, one offline HTML file, a share link, an embed for any page.
  • Operation maps: sessions, people and the handoffs between them, drawn and checked. Never compiled.
  • Observation: a hook that records when sessions and subagents start and stop, in Claude Code and in Codex, and a live view of it. It never steers.
  • An MCP server with four tools for a running session: plan, note, running, validate.

What it cannot do yet

  • Compile for Codex, or any second harness.
  • Let an agent author a graph through tools alone, or from a chat.
  • Install from npm.
  • Nest one graph in another, or link two graphs.
  • Edit a map in the app, save a map in the library, or bind a map's session to its events in the map itself.

Ideas and recommendations

My view on each thing you raised. React under any of them; the bigger choices are also cards at the top.

Subgroophs: a grooph inside a grooph

Yes, and it fits what is there. Today a fragment template can be copied into a graph, and "a graph pointing at another graph" is on the deferred list. A subgrooph is that pointer.

  • In the document: a node whose kind is a graph, naming another document by id and version, with its exits mapped to edges: pass, fail, halt.
  • At compile time it is inlined. The child's agents become subagents of the same lead, with their ids prefixed. This keeps the rule that a graph is one session, and it is forced: a subagent in Claude Code cannot start subagents of its own.
  • The validator checks the whole. A child's loop must still end inside the parent. A child can tighten the parent's brakes and never loosen them. No graph may contain itself.
  • In the picture: the node shows the child's glyph. Tap to step in; a trail leads back out. A long graph becomes a short one with rooms.
  • For agents: two operations, insert a graph as a node and expand it in place. grooph flatten prints what will actually run.

It changes the product contract, so it needs an amendment. I would draft it first and build it second.

Intergroophs: linking groophs across sessions and projects

The operation map already draws sessions and the handoffs between them. An intergrooph is a handoff that names a graph at each end.

  • A port on each graph: what leaves one (a stop, an artifact) and what the other takes in (its goal, a slot).
  • A carrier, as every handoff has: a branch, a pull request, a message, a schedule, a person.
  • Rules: a cycle across graphs needs a stop or a person, as a loop inside one does. The map already counts what moves only when a person moves it.
  • In the app: a session's card on the map opens its graph, and the link shows as an arc between two graphs' doors.

The deferred list has the pieces: a binding from a map session to its events, maps in the library, editing a map in the app. I would do those with it.

What else, in the same family

  • For-each. One sub-graph run once per item in a list (per file, per ticket), with a join. The most useful missing piece after nesting.
  • Twins. One graph compiled for two harnesses and run side by side, with the two records laid over each other. The game experiment is the first twin.
  • Lenses. The same picture with one thing lit: who may write what, what costs most, which steps cannot be undone, which nodes have a record behind them.
  • Pulses. A small graph attached to another and started by a schedule or an event: a patrol, a watchdog.
  • Imports. A subgrooph pinned by name and version from a registry, as a package is.
  • Time. A run laid out round by round, a ladder, so a loop that turned four times reads as four rungs.

My order: subgroophs, then for-each, then intergroophs on the map, then lenses.

Other views, 3D, and the long map

The tall map is hard to read because one column is the wrong shape for a wide screen and nineteen arcs share one margin. There are cheaper fixes than 3D, and 3D is still worth having.

  • Lanes side by side on a wide screen. Small change, big gain.
  • A sequence view: each session a column, each handoff a numbered arrow in order. It answers "what happens after what".
  • A matrix: who hands to whom, at a glance, in one screen.
  • A ring: sessions around a circle, handoffs as chords.
  • 3D: lanes as planes in depth, nesting as depth, time as a slider. Good for seeing structure and for showing someone. Worse for reading words. It must stay a view, never the document, and load only when asked, so the speed budget is untouched.

Sketches of all of these on your real map are in the design studio, linked from its card above when it is published.

The game experiment

One spec, one graph, built twice: once in Claude Code and once in Codex, each in its own new repository, each with the same time limit. I want it as much as you do, and I want it to be a fair test.

  • It needs two things first: the Codex target, and the tier map so no run uses Fable.
  • The graph: a new template made for it. A planner cuts the game into pieces; builders own one piece each; a playtest critic drives the game in a real browser and files what is broken; a polish loop ends on a bar you can see; you approve at one gate.
  • The bar: one finished slice of a game, not a whole one. A browser game built in one sitting can be striking. It will not be a studio title, and the spec should not ask for one or both runs fail the same way and teach nothing.
  • Scoring: a checklist both must pass (it loads, it holds its frame rate, nothing in the console, the core loop completes), then you play both blind and rank them.
  • Stack: three.js, with models made in code or with Blender run from a script. Both runs may upgrade their tools.

The cards above ask for the genre, the time limit and the repositories.

The audit loop

Before a claim is published, Codex reads it as a skeptic. One Claude lane writes the handoff and reconciles what comes back. You carry one prompt each way. Codex changes nothing. A new experiment is designed inside the loop and run outside it. The loop ends when neither side holds a finding that blocks a claim, or when you call it.
