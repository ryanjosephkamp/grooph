1. The templates page: search, filter, sort, and a shape glyph

Answer: yes, and it is cheaper than it looks. The data is already there: every template carries a coarse profile (cost, speed, rigor), tags, a kind, and the app already draws a read-only canvas for a graph opened from a link. Nothing here touches the graph document, and the spec explicitly allows a Mermaid-like projection as a view.

Search, filter, sort. Search over title, summary, when-to-use and tags; filter by kind, by each profile axis and by tag; sort by cost, speed, rigor or name. One screen, one slice. The same index should drive the design skill's template list so an agent and a human see the same ordering.

The glyph. A pure function in core, glyph(document), that returns a small SVG with no words: node kinds as shapes, edge kinds as line styles, loops as a dashed hull, gates and irreversible steps visibly different. Because it lives in core it renders identically in the CLI (grooph glyph), on the site's template list and compare cards, in the proving write-ups, and as a file you can save. A first draft of the design language, using shapes the canvas already distinguishes:

review-gate as a glyph: square builder, diamond critic, octagon human gate, filled dot stop; solid pass edges, dashed fail edge back, dotted gate-reject edge; dashed hull is the loop. Hand-drawn here; the real one is generated from the document.

Mermaid. A one-way projection, grooph mermaid <file>: a flowchart with one subgraph per loop, edge labels from the edge's condition, and a note per stop. It is easy because the document is already a graph, and it costs nothing in the document itself. It cannot round-trip (Mermaid has no loops, stops or bars), and it should never be edited in place of the document; the spec's "document first" rule stays.

Cost and placement. One implementer slice for the web work, with the glyph and the Mermaid projection in core and the CLI in the same slice so the site, the CLI and the write-ups share one drawing. No proving spend. I put it after the credits slice and before the comparison because the glyph also improves the compare view and the proving write-ups.

2. Are the templates too small?

Answer: it is deliberate, and it is not the end state. The sixteen are the spec's own pattern list, one to one. They range from three to eight nodes and one to six agents. Three rules made them small: the spec's "smallest graph that works", its lesson that same-role harsh-critic language adds nothing while structure does, and the "latitude over procedure" rule that keeps briefs to purpose, limits and outputs. The proving ground bore this out: the smallest graphs ended cleanest, and the six-agent bank costs about $2.80 a round.

What "bigger" should mean. Not more adjectives or longer briefs, but composition: fragments inserted into hosts (the runner proved this with the irreversible gate inside a grind loop), nested loops (fresh-grind-rare-judge), and organisation-shaped graphs where several small shapes are wired together with real ownership. Each one is proved before it ships, so a large template that does not earn its cost never enters the library.

4. Paired comparisons: grooph versus a big prompt

Answer: yes, and it is the most important thing on this list. Today the honest answer to "is a loop graph better than not using one" is unknown. The proving ground shows that packages drive sessions as designed; it says nothing about whether the design beats a plain prompt. The spec forbids claiming a graph beats a named product; it says nothing against measuring a graph against no graph, and that is the evidence the project needs. I would move it ahead of the new templates.

The protocol I recommend

  • Per template, one designed project with a written task, a test command, and held-out cases the builder never sees (the proving ground's task folders already have this shape, and several can be reused as they are).
  • Three arms, not two. (A) the grooph template through its package, headless, as the proving runs go. (B) one big prompt: the same task and the same workflow described in prose in a single prompt, one session, same model and effort, no package. (C) the big prompt inside a traditional loop: the same prompt piped into fresh sessions by a ralph-style bash loop with the same round cap. B measures the graph against nothing; C measures it against the looping people already do. Two arms would leave one of those unanswered.
  • Same everything else. Same model and effort for the lead, same dollar cap per run, same permission allowlist, same harness version, all recorded.
  • Two runs per arm minimum, three where a template's bet involves judgment (taste-polish, the bank). With n this small, report ranges, not means, and say so.
  • Two kinds of measure. Objective: held-out pass rate, tests passing, defects a fresh judge finds, files touched outside scope. Process: cost, wall time, harness turns, permission refusals, whether a human had to intervene. Plus one blind judgment: a frontier critic in a fresh context compares the arms' outputs with labels stripped and order randomised, and says which is better and why. The judge's verdict is one measure among several, never the headline.
  • Pre-registered. Each project's expected outcome and what would count as the graph losing is written before any run, in the same spirit as the proving ground's expect files.
  • Records kept like the proving records: evidence never edited, a red result published red, decision 0009 applies.

Scope and cost

Start with four templates whose bar is most objective: grind-loop, review-gate, red-team-loop and spec-then-loop. Four projects, three arms, two runs each is 24 runs at roughly $1 to $4 each, plus judge runs, so about $60 to $90. I would give comparisons their own ledger with a $100 cap rather than stretch the proving ledger. Extending to all sixteen later is another $200 to $300 and should wait for what the first four show.

What it can and cannot show

It can show whether, on small designed tasks with one model, a graph produces better held-out results, fewer defects, or lower cost than a prompt or a plain loop, and by how much in a range. It cannot show that a graph beats a human team, a named product, or a different model, and with n of two it cannot show a small difference at all. The write-up says which of these each pair showed.
