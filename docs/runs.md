# Runs: notes back, adoption, and the monitor

Normative for slice 0008. A run leaves a folder behind; this page says how grooph reads it, shows it, and lets the human adopt what the run learned. grooph still executes nothing and calls no model: everything here is reading files a harness wrote.

## 1. The run folder (what packages already write)

```
.grooph/<graph-id>/runs/<run-id>/
  PROGRESS.md            human-readable
  notes.jsonl            one RunNote per line (graph-ir §6), append-only
  graph.grooph.json      the run's working copy (graph-ir §2)
  …                      whatever the lead materialized: round-<n>/, evidence files, amend-*.ops.json
```

One addition to the package contract, so a monitor can show what is running and not only what finished: **the lead appends a note with `"outcome":"started"` when it dispatches a node** (`at: node:<id>`, `round` when inside a loop), and the usual note when the node completes. One short line per dispatch. Lead-brief §8 says so; older runs simply have no started notes.

## 2. Core (pure)

| Function | Does |
|---|---|
| `parseRunNotes(text)` | Line-tolerant: returns `{ notes, issues }`; a malformed line is an issue with its line number, never a throw. |
| `summarizeRun(notes, graph)` | `RunSummary`: run id, state (`running` · `halted` · `ended`), outcome, started/ended, per node `{ state: pending · running · passed · failed · halted, runs, lastOutcome, lastVerdict, round }`, per loop `{ round, lastStop }`, amendments, proposals, cost totals per measure, and the ordered timeline. A node is `running` when its last note is `started`. |
| `diffGraphs(source, working)` | The change list between two documents as a grooph op list where ops can express it, plus a plain-language line per change; layout and notes ignored. |
| `adoptWorkingCopy(source, working, { run })` | The working copy as the next version: `version + 1`, source `id` and `name` kept, `lineage.from = "<id>@<old version>"`, run notes not copied. Refuses when the working copy has export errors. |
| `checkAdoption(source, adopted, { allow })` | What adoption would write, held to the brakes of the source it replaces (amendment A-008): every difference by name (`loop:review.stops`), with why it loosens a brake or what undoing it would loosen (it tightens one); `refused` is the changes that loosen a brake and were not asked for in `allow`. The comparison is the one a subgrooph's refresh is held to (`templates.md`, "Refreshing"), with the adaptation level beside it. Not in the web app's build. |
| `buildRunBundle({ source, working, notesText, progress? })` / `parseRunBundle` | A self-contained `*.grooph-run.json` (`{ groophRun: 0, … }`) for import and for share links (`kind: "run"` joins `docs/executive.md` §2; same untrusted-input rules). |

Run data lives **beside** the graph, not inside it: the document stays small (spec §4.7). "Pin to graph" copies a chosen note into `doc.notes`, which is what spec §5.7 means by notes attaching to nodes, edges and the graph.

## 3. CLI

```
grooph runs list [<dir>]                         runs under .grooph/*/runs/, newest first: id, graph, state, rounds, stop
grooph runs show <run dir> [--json]              the summary, amendments, proposals, timeline
grooph runs bundle <run dir> --out <file>        self-contained bundle
grooph share <run dir>                           a link that opens the run view (warns when long; bundle file is the fallback)
grooph adopt <run dir> [--into <graph file>] [--allow <change>]... [--write]   show the diff; with --write, write the next version (default target .grooph/graphs/<id>.grooph.json)
grooph watch [<run dir> | <graph dir>] [--sessions] [--events <source>]... [--port 4174] [--host 127.0.0.1] [--open]
grooph hooks install | status | remove [--harness claude-code,codex] [--tools] [--local]     the event hook (§6)
grooph sessions [<source>...] [--json]            what the hook has recorded, as text or data
```

`watch` serves the built web app and one read-only JSON endpoint with the current bundle, re-read from disk on each request; with a graph dir it follows the newest run. It binds to `127.0.0.1` unless `--host` is given; with another host it prints that anyone on that network can read the run, and the URL to open from a phone. It writes nothing and needs no credentials. It is a local viewer, not a backend (decision 0001 anticipated it).

## 4. The run view (web)

`#/run` opens a bundle from a link, an imported file, or the `watch` endpoint (polled every two seconds while the run is not ended).

- **Canvas with state.** Pending nodes quiet, running nodes pulse (a static ring under `prefers-reduced-motion`), passed and failed take the semantic colors already in the tokens, halted amber. Loops show their round. State is shown by icon and label as well as color.
- **Timeline.** Notes in order, newest first while live; tapping one highlights its object. Amendments and proposals are marked.
- **What the run changed.** The `diffGraphs` list between source and working copy, each line tied to the amendment note that explains it. **Adopt as version N+1** checks the working copy's brakes against the source's (§5) and, when none is loosened, saves the adopted graph to the library (the source stays); **Discard** does nothing to the source and says so.
- **Proposals** are listed with their patch; "Apply to a copy" applies an op-list patch to a new version for the human to inspect. Nothing is applied automatically (spec §11). The copy is the run's working copy with the proposal applied, so the run's own amendments are in it. It is compared with the graph the run came from by the comparison adoption uses, and the page says by name what the copy loosens (`loop:sandwich.stops raises the round cap from 5 to 9`) and what is noted, without laying it at the proposal or at the run; it is saved either way, since a proposal is how a run asks for a brake to be loosened and the answer is the person's. Two cases are said and not compared: a copy the patch leaves outside the schema (the page says it has errors, and that its brakes were not compared), and a comparison that could not be fetched (the copy is saved, and the page says to read its limits). Unlike an adoption, a copy with errors is still compared where it is a valid graph, and what it tightens is not listed.
- **Pin to graph** on any note.
- Runs imported into the app are stored beside graphs on the device and listed under the graph they belong to.

## 5. Details fixed by slice 0008

- The live endpoint is `/grooph/api/run.json` on the `watch` server, and the app's live route is `#/run?live` with that fixed same-origin path; no URL parameter names an endpoint, so a crafted link cannot make the app fetch elsewhere. A stored run opens at `#/run/<key>`.
- **`grooph adopt` holds a working copy to the source's brakes.** A run may tighten a brake and never loosen one (`graph-ir.md` §2); until 2026-10-05 that was a sentence in the lead's brief and nothing checked it, and the audit of 0.3.0's claims showed a working copy with its round cap and budget raised being adopted. Now what would be written is compared with the source on the whole graph (`checkAdoption`): a change that removes or loosens a brake is listed by name with its reasons, and `--write` is refused until each is asked for with `--allow <name>`; one that tightens a brake is adopted with the rest, and said. That label means only that undoing the change would lose something by this comparison; it is no finding that the change is safe, and several of the limits listed below print under it. A change that brings in an answer a gate did not give, or a step marked irreversible that the graph did not have, is named and not called a tightening for that, though undoing it would take an answer or a mark away (where the same change carries a second reason, a new answer that leads to a new gate, it is listed under "tightens a brake" as well): it lets a person or a run do what it could not before, and a program cannot tell a way to say no from a way on. (Until 2026-10-05 the command printed both under "tightens a brake"; the reader of the export door asked whether that was true of a new step told to publish.) Without `--write` the report is the same and nothing changes. Adoption is whole: nothing is held back while the rest is written. Since amendment A-019 a check is among the brakes: a change to what it runs or what counts as a pass, its removal, a change to an edge that leaves it, or a new way to what its pass led to, is refused by name like the rest (`node:tests.check`, `edge:e-tests-pass.when`). The first cut of that rule let a change to such an edge through whenever the comparison would call it a tightening, and a fresh reader got two working copies of the kept grind-loop record written through it: a failure led to a second stop that ends in success with an approval asked beside it, and the loop given a bar of the builder's own word with a stop on it. So only an approval newly asked on such an edge and more evidence handed to a critic pass unasked, and a bar or a stop on "bar passed" given to a loop that a check judges is held. A second reader, given the first one's scripts, got three more through that: a critic from elsewhere in the graph named among the loop's members beside the bar, evidence replaced while the edge's target was made a critic, and the audit's own third probe on the retrospective template, whose round cap already leads on to the end. A third, given both sets of scripts, found the first two clauses and the bar's rule holding and one more way through the last: on that same template, a new budget or a second loop whose cap leads straight to the end. Each is closed and a test; what the readers left as limits is in `templates.md`. An honest change now costs an `--allow` in two common places: a gate put behind a check's pass, and evidence added on a check's edge to a builder (a lead that adds the failing output for the builder is held at adoption). That is the price of a rule a program can apply, and the line that holds either one says so. Those two are not the whole price: an edge that leaves a check, given another id, is held under two names (the old one removed, the new one added), and a `label` or a `retry` on such an edge is held as any other change to it is. And a name covers more than the line may show. `node:<id>.check` is one name for a check's whole definition: allowed for a pass text reworded, it carries a command made `true` in the same working copy, and the line then reads "(run, pass)". `edge:<id>.evidence` is one name whether evidence was added or swapped. A check under another id is held as a removal, and allowing that name allows every change made to that check under its new id and every way round it. The line says so, and shows what comes in: `node:tests  removes a check, while a check the graph has not comes in ("test-suite": runs "true", passes on "exit code 0 and no test skipped"): if that is this check under another id, allowing this name allows every change made to it and every way round it`. In a working copy where a check goes while another comes in, no change is called a tightening: a bar or a budget put round the check under its new id would read as a brake gained. Each such change is still listed by name, under "not judged". Read the working copy before allowing a removal. A run that comes to end in success without a check's pass, or a critic's, is held where a run could not already end in success without that pass, by any way: a failing verdict led to a stop that ends in success, whether the run adds that stop, the graph had it, a step on the way is made one, or a stop that halted is given `outcome: success` (`node:failed.outcome  a run could end in success at "failed", a way that does not pass "pass" from the check "tests"`). The pass is the verdict written `pass`; a judge with none, whose verdicts are two or more words of its own ("clean" and "finding"), is asked of each word, since a program cannot tell which is the good one. Where a run already could (through a person's yes, on a second word that passes, by the loop's bar, by an exit the builder has of its own), a new way to the end on a failing verdict is not seen; and a critic with one word that is not written `pass` is not asked at all. Each of those shapes is a critic's, is the same on the comparison as it was before this rule, and is named in the list below. And a stop that halts, made to end in success, is held wherever it stands, also where no verdict leads to it: a cap or a plain step that led there to stop the run would then end it well. It is held by its own id, its outcome set so or taken away; a plain step's edge led from it to a stop that ends in success is not (the list below). What the comparison covers and what it does not is in `templates.md`, "Refreshing"; a brief, a model tier, a node's permissions and a policy of another kind are shown among the changes and are not refused, and neither is a way round a loop that a person newly opens each time: that one is printed as a note, by name, since the loop's cap then counts the rounds between that person's decisions. A fresh reader asked to break this got five kinds of working copy through its first version (a loop put around a capped loop, a second way round through a new step, a stop that leads back in set before the stops that halt, a second edge beside an approval or around a gate, a step taken out of a loop's members), and a second reader three more through the rules written in answer (a loop left as a shell with its work under other names, an approval gone around by a stop, another loop's back edge moved inside the loop); each is refused now and is a test, and **the list of what a brake is has not been shown complete**: every reader so far has found something. `--into` may not name the source or the run's working copy, by any spelling or link: adopt never writes either. **The web app's "Adopt as version N+1" makes the same comparison** (`apps/web/src/ui/run/brakes.tsx`, with core's `checkAdoption` behind it): a working copy that loosens a brake is not saved, and the page lists each such change by name with its reasons, in the command's words, with the command that adopts it on purpose to copy (`adoptCommandLine`, the function the command's own message uses; a test runs what the page shows). There is no way to say yes in the app. A tightening is adopted and said, and so is the note. The comparison is a piece of the app fetched when Adopt is pressed and held by the service worker, so it works with no network after one visit; if it cannot be had, nothing is saved and the page says so. "Apply to a copy" on a proposal is not refused: by `graph-ir.md` §2 a loosening is a proposal for the human, and applying one is that human's act. The copy is saved, and the page then says which brakes it loosens against the graph the run came from, each by name with its reason, by the same comparison; the copy is the run's working copy with the proposal applied, so the page says that either may have done it. A copy that is not a valid graph is not compared, and the page says that instead.
- **A person's step is not run** (amendment A-020): no package is made of a graph that has one, so no working copy of one exists, and the comparison holds nothing about `by`. Were a run's working copy to mark a step as a person's, the check a run makes of its copy and adoption both refuse it for an export error (`E_PERSON_STEP_NOT_COMPILED`). The comparison itself names the change `node:<id>.by` and gives it no label, whichever way it went: holding a person's step made an agent's is for the amendment that lets a harness run one.
- **What adoption does not hold**, so that nobody takes the comparison for more than it is. Each of these is adopted with nothing refused, and each is also in `templates.md` under "Refreshing", which is the same comparison:
  - A stop that leads on, lowered or added, in a loop that holds no stop that halts and none where a person is asked (the built-in retrospective, whose cap and budget both lead to the wrap-up). The run then comes sooner to where the stop leads. It is adopted, and named as not judged; until 2026-10-06 it was printed under "tightens a brake". Where the loop holds a stop that halts or asks, it is the next item.
  - **A loop's stops are compared as a run fires them, since 2026-10-06**, at `grooph adopt --write`, at `grooph export --into`, at a subgrooph's refresh and in the app alike. A loop's stops are tried at the end of every pass, in document order, and the first that fires wins (`graph-ir.md` §2). Until then the comparison read each stop's size and where it leads, kind by kind: not the order the stops stand in, and nothing of a kind of stop the source did not have. The second harness found two limits swapped being adopted (audit 0001, round two, finding F1): a limit that halts and one that leads on, which can come due on the same pass, with the one that leads on put first. A fresh reader of that round's reconciliation found a second way: a round cap that leads on, new to a loop that held only a budget that halts, ahead of it or behind it, adopted and printed under "tightens a brake" where no check and no critic stood before the place it led. Both were so in 0.4.0. The first cut of the repair was then read by a fresh reader of the driver's, who found the rule holding and three more ways beside it, closed in the same change and listed here with the rest. **What is held, exactly:**
    - *What is protected, in the source:* a round cap or a budget that halts (it names no `then`, or one that is a human gate or a stop that halts), and every stop where a person is asked, with a `then` or with none, each time it would ask.
    - *What is asked about, in the copy:* a stop that leads on with nobody asked. That is a round cap, a budget, or a stop on diminishing returns or on invalid evidence, whose `then` is a step or a stop that does not halt; and a stop on "bar passed", with a `then` or with none (the run then follows the loop's pass edges), in a loop where no critic the loop had is among its members still.
    - *The question:* is there a run in which the source would have halted or asked a person on some pass, and the copy leads on by that stop, on that pass or an earlier one? If there is, the change is held by the loop's name (`loop:<id>.stops`) until it is asked for, whether the stop is new, moved, lowered or as it was. A stop where a person is asked ends nothing, in either version: the run is taken to go on from it as if the person had said so, and the stops are tried again after the next pass. So a person's stop in the copy excuses nothing that fires on a later pass. On the pass it fires it is still the first that fires, and nothing behind it is obeyed on that pass.
    - *What it takes as known of when a stop is due:* a cap of n rounds, on pass n and after; a person asked every round, on every pass; a stop on diminishing returns or on invalid evidence over n rounds, not before pass n; a budget, on any pass, since what a pass spends is not known; a person asked every n rounds, n over one, on no pass before the nth and from there on any pass (that it is every nth exactly is not reckoned with). **What it does not know it takes to be possible.**
    - *The line* names the stop, what became of it, and a limit it would come before: `the round cap of 1 that leads on to "done" would come into the loop, and could fire before the budget of 2 dispatches that halts the run`; `the budget of 2 dispatches that leads on to "done" would be moved ahead of the round cap of 1 that halts the run, and could fire on the same pass`; `the round cap of 1 that leads on to "judge" would go from 2 to 1, and could fire on the same pass as the budget of 8 dispatches that halts the run, where it would be the one obeyed`. Where an older line speaks of the same kind of stop, both are said.
    - *A second loop put on the loop's back edge*, whose stops fall on the same passes: a stop that leads on among its stops, which it did not hold before, is held (`loop:<its id>`). How the stops of two loops fall on one pass is written nowhere, so it is taken to be able to fire first.
    - *The words "tightens a brake"* are said of no change to a loop's stops that brings in a stop that leads on, or puts one ahead of a stop it stood behind: a stop with a `then`, wherever that leads (a step, a human gate, a stop that halts, on from a person who was asked), or a stop on "bar passed". Such a change is listed as not judged, whatever else it does to those stops. A new or lowered stop that halts, a person's among them, in a change that brings in none of those, is a tightening as before.

    **What it costs an honest change, which is one `--allow` each time.** Lowering a limit that leads on, where the loop also holds a limit that halts or a stop where a person is asked, is not a tightening: the lowered limit can come due on a pass on which the other would have halted the run, and the run then goes on. On 4,000 lists of stops made at random, changed by one honest edit at a time (the driver's reader's script, run on this change), a limit that leads on, lowered by one, is held in 558 of 747 where it is a budget, 293 of 507 where it is a round cap, and 371 of 486 where it counts rounds without progress; for most of those a run exists in which the copy leads on at a pass where the source halts. And "ask a person every n rounds", lowered by one, is held in 100 of 1,185: asked every second round, a person is no longer asked on the third, and a stop that leads on behind theirs can fire on it. Among the built-in templates and the plan templates, of 575 honest edits to a loop's stops one is held: on the debate, the cap of two rounds that leads to the judge, lowered to one, for the budget of eight dispatches (three agents a round cannot spend eight on the first pass; the comparison does not reason about what a pass spends). A second limit that leads to the judge is held ahead of that budget and adopted behind it. Nothing else of those edits changes its verdict: a new stop that halts, one that halts lowered or moved ahead, and one that leads on moved behind, are adopted.

    **What this still does not hold:**
    - *"Bar passed" in a loop a critic judges, moved ahead of a limit that halts, or new.* A run whose last allowed pass meets the bar then goes on where it halted. A critic's pass is what the loop is for, and what the bar leads to is held by what a run reaches around a critic; its place among the stops is not.
    - *A new stop where a person is asked.* It is named and not refused, wherever it stands and wherever the run goes on from it: the person is the brake on it. (It is held as before where it leads past a critic or a check, or comes before a stop of its own kind that halts.)
    - *A stop that halts on diminishing returns or on invalid evidence.* Neither is on amendment A-008's list. Its removal is not held, and nothing asks whether a stop that leads on comes before it.
    - *A new way to an end that is no change to that loop's stops*, where only a limit stands before the end, and no check, critic or gate. A plain new edge from a step of the loop straight to the end is adopted. So is a new stop that leads on in a loop inside the one that holds the limit (the other way round, and a second loop on the same back edge, are held). So is a new step put on the loop's round with a loop of one node of its own and a cap of one that leads on. Amendment A-008 lets a lead add edges; whether a new road to an end is a brake where nothing was checking is a question about the contract, and it is with the owner.
    - *How much a pass spends, and on which passes a person asked every n rounds is asked.* Neither is reckoned with, which errs toward holding: a budget of dispatches that could not in fact be reached on the first pass is taken to be able to, and a person asked every third round is taken to be asked, perhaps, on the fourth.

    The audit's three probes are `experiments/audits/0001-claims-as-of-0-3-0/tools/stop-order-probe.mjs`, `stop-added-ahead-probe.mjs` and `stops-in-built-ins-probe.mjs`, with what each printed at 0.3.0 and at 0.4.0 in that audit's `round-02/lane-notes/reconcile/`. With this change both swaps and all six added stops are refused through both commands; and of 1,306 new leading-on stops tried on the 26 loops of the built-in templates and the plan templates, the 77 not held are 69 where a person is asked and 8 that lead to a human gate, none of them called a tightening (at 0.4.0, 84: seven more on the debate, each leading where its cap leads). A model of the firing rule, written apart from the comparison, is in its tests (`packages/core/test/stops-as-fired.test.ts`), and the comparison is held to it on lists made at random: every run the model finds is held, and where no person is asked on only some passes, nothing else is. That is what was tried, not a proof, and this rule has not been read by a second harness.
  - A way round a critic's verdict where a round cap of its loop already leads on: an edge from the builder to the step the cap leads to, or past it, straight to the end. For a check that is held (its verdict is asked a second time, without the brakes that already fired); for a critic the second asking is not made.
  - The edge that leads into a check, made conditional, so that the check is never run and nothing leads on from it.
  - A value a subgrooph's group holds for a check's command, changed in a working copy. Adoption takes it; the subgrooph's next refresh holds the check it would change.
  - A second loop put over the members of a loop that a critic judges and that holds no check, with a looser bar of its own; and a bar given to a loop that a critic and a check both judged and that had none, alone or with a stop on "bar passed" that names no `then` (one that names `then`, and so leads on past the check, is held). Adding a bar reads as a tightening, whoever's word the bar is.
  - A gate's answer led to a stop that ends in success which the run adds, or to one the graph had that a run already reached another way; or a step on that answer's way made such a stop. It may be printed under "tightens a brake", for a way back into the stop the answer left that undoing it would open. (Where the stop it left is then led to by nothing, the copy is refused for that: a run would start there.) Led to a stop that only the gate's other answer reached, it is held, by the rule for what a run reaches without an answer. Every answer at a gate is the person's, and how a run ends is asked of a gate as a whole, not of its answers one by one. (For a check's verdict and a critic's it is asked of the pass, and each of these is held.)
  - A way round a loop that a person newly opens each time: a new answer at a gate that leads back, a stop where a person is asked that continues in the loop, an edge that needs approval. It is printed as a note, by name, and not refused.
  - Two decisions at once. A critic's failing verdict leads to a gate, and only the person's yes takes it on to the end; a second edge on that verdict, straight to the end, is adopted. Asked of the critic's pass alone, a run on "fail" could already end in success, through the person; asked of the person alone, a run could already end with nobody asked, on a pass. The two are not asked together. On the built-in patrol it is the investigator's "finding" led to where its "clean" leads. (The verdict's own edge led there, away from the gate, is held, since nothing then leads to the gate; and for a check any edge added where it leaves is held.)
  - A critic's failing verdict taken to the end where a run could already end in success without the critic's pass, or where there is no pass to ask of. What is asked is whether a run could not end in success without the pass before and can afterwards, by any way; where it already could, a new way there shows nothing. Each of these is written by `grooph adopt --write` with nothing refused, and each is a critic's (for a check any edge added where it leaves is held):
    - *A second word that passes.* The critic says "pass" or "pass-with-notes", both leading to the end, or "fail", back to the builder, and no person stands before the end. A second edge on "fail" straight to the end is adopted, and so is an edge from the critic with no `when`. This is the common "approve with nits" shape.
    - *The pass is the loop's bar.* The critic's only edge is "fail", and a stop on "bar passed" leads on to the end. A second "fail" edge to the end is adopted, and printed under "tightens a brake" ("undoing it: nothing would lead to "done", so a run would start there"), which is not true of it.
    - *One word, and not written `pass`.* A critic that says only "approved": a new verdict led to a new stop that ends in success is adopted. Written `pass`, it is refused; a judge is asked of each word only where it has two or more.
    - *The builder has an exit of its own.* "fail" returns to a builder that has a "nothing to do" edge to a stop that ends in success. A second "fail" edge to a new stop that ends in success is adopted.
  - A plain step's edge, where no check, critic or person stands, led from a stop that halts to a stop that ends in success which the run adds (the same stop under another id among them), or to one the graph had that a run already reached another way. A stop that halts is held by its own id, and not by where a plain step's edge leads.
  - A gate's answer led on to a new step. A person's yes at a merge gate, led to a new step told to publish and from there to the end, is adopted and listed with no label (`edge:<id>.to`, `node:<id>`); where the step is marked irreversible it is named as not judged. A gate's prompt is not held either, so a person may be asked one thing and their yes do two. What is held of an answer is which answer an edge is taken on, that an answer the gate gave still leads somewhere, and what a run reaches without it.
  - A new answer at a gate. It is named as not judged. Led to a new stop that halts, it is a way to say no; led to a new stop that ends in success, it is the limit named earlier in this list (a gate's answer led to a stop that ends in success); led to what only another answer reached, it is held.
  - A step's effort; what a step is handed and what it is to write (its `inputs` and `outputs`, a critic's among them); evidence on an edge that neither leads into a critic nor leaves a check; and the graph's goal, with its "Done when". Each is listed among the run's changes by name, with no label, and adopted. `templates.md` names the rest of what is shown and applied: a brief, a gate's prompt, a model tier, a critic's permissions, a bar's answer key or what it inspects, a loop's mode.
  - `grooph export <graph> --into <dir>`, and the `grooph_export` tool, compared nothing until the evening of 2026-10-05: a graph whose round cap was 5, exported over its package with 50, exited 0 with no word, and so did a run's working copy that `grooph adopt --write` had just refused (`experiments/audits/0001-claims-as-of-0-3-0/tools/export-door-probe.sh`, with what it printed in `round-02/lane-notes/export-door-probe.txt`). Both now make this comparison, on the owner's word (amendment A-019's note): over a package in place for the same graph id, while the graph it keeps can be read as that package's graph and its brief and mapping notes there are what it compiles to, a change that may remove or loosen a brake is listed and nothing is written until it is asked for by name (`--allow`, or the tool's `allow`). **The package's kept graph is compared again at export after an adoption, by design**: a graph can reach a package without `adopt`, so `adopt` prints its next step with the same `--allow` names. What is not held there: a first export; a graph under a new id, which is a second package beside the first; a package whose kept graph is gone or does not match its files, where nothing is called compared and the export waits for `--uncompared` (the tool for `replace`); and a hand that rewrites the kept graph together with those two files, or takes an irreversible marker off it, which neither file shows. No command of grooph's but `export` writes a kept graph. Not read by a second harness.
- `adopt --write` is refused when the source's version differs from the version the run started from (the source moved on), or when the target already holds something else; adopting the same run twice is a no-op. `lineage.from` of an adopted version names the previous version of the same graph.
- The stop that fired is read from a loop note's `stop` field when present (graph-ir §6) and inferred from its text for older runs.
- The timeline is in append order; timestamps are shown, not trusted for ordering.

## 6. Hook-written events (slice 0027, amendment A-012)

A second file beside the run notes, written by the harness's hooks and not by the lead: `.grooph/events/<session id>.jsonl`, one line when a session or a subagent starts or stops. [`subagents.md`](subagents.md) has its shape, how to install the hook in Claude Code and in Codex, and what each harness tells it.

- `grooph watch` serves it at `/grooph/api/live.json`, read from disk on every request like the run, and merges more sources given with `--events`. `grooph watch --sessions` opens on `#/live`, the sessions and their subagents; so does `grooph watch` in a project that has events and no run.
- In the run view, a node is drawn running from the moment the hook sees a subagent named `<graph-id>--<node-id>` start, whether or not the lead has written its `started` note (`nodesLive` and `overlayRun` in core). Only events from after the run's first timestamp count. An outcome is still the lead's note: a hook cannot know a verdict.
- The package, the lead's brief and the run folder are unchanged. A run does not depend on the hook, and the hook adds no instruction to any agent.

## 7. Out of scope here

Token accounting from the harness; a hosted monitor; notifications; editing a run. The monitor must never add instructions to a package beyond the one started note. Asking the lead to write fewer notes because a hook now writes them is slice 0021, and needs its own proving run.
