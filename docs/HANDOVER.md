# Handover: moving grooph to another Claude account

Most of grooph is portable already. This file names the part that is not, so a fresh session signed in as someone else can pick the project up from files alone.

Written 2026-09-19, against the account that built slices 0001–0009. Re-run the `account-handover` skill to audit it after anything is published or scheduled.

## The short version

grooph is unusually clean to hand over: **no routine, no scheduled task, no connector, and nothing the project reads at run time belongs to a Claude account.** The only account-owned things are three published pages, and their sources are now in the repository. There is nothing to turn off at switch time and nothing that can collide.

## What moves on its own

Signing in as another account at the same path changes none of this. It is keyed to the filesystem, not to who is signed in.

| Where | What it holds |
|---|---|
| the repository | everything that defines the project: `spec/`, `docs/`, `handoffs/` (protocol, every handoff, handback and review), `patterns/`, `fixtures/`, `experiments/` (the proving records), `plugins/grooph/` (the `grooph-design` skill), `packages/`, `apps/web`, `.grooph/` (placed packages, graphs, the one real run record) |
| `~/.claude/projects/-Users-noir-Documents-grooph/` | this project's **memory files and every past session's transcript**, about 56 MB. The folder is named after the path, not the account, so it survives the switch. Most people expect to lose this and do not. |
| `~/.local/bin/grooph` → `packages/cli/bin/grooph.js` | the `grooph` command. A symlink into the clone; unaffected. |
| `~/.claude/skills/grooph-design/` → `plugins/grooph/skills/grooph-design/` | `/grooph-design` in any project on this machine. A symlink into the clone; unaffected. |
| the system keyring (`gh`) | the GitHub login. Pushes, CI and the Pages deploy are tied to the **GitHub** account `ryanjosephkamp`, not to the Claude account. |

The live site, the published template library and the published proving runs all keep working:
https://ryanjosephkamp.github.io/grooph/ · `…/patterns/index.json` · `…/experiments/patterns/ledger.json`

## What does not move

### Three published Artifacts

Each belongs to the account that published it. The new account sees nothing at these URLs.

Sources and current URLs: [`handoffs/briefs/README.md`](../handoffs/briefs/README.md). Each is **archived, not rebuilt** — they are hand-written HTML, not generated by a command. To recreate one, publish its source file again from the new account and record the new URL in that table.

**Deliberately abandoned, and it costs nothing:** their substance lives in `docs/PROGRESS.md`, `docs/PLAN.md` and each slice's `REVIEW.md`. A brief is a phone-shaped restatement of those files at a moment in time. Do not republish them on the new account unless you want the bookmarks back; the project reads none of them.

### The synced-skills folder

`~/.claude/skills/synced/<id>_<account uuid>/` is per account. Nothing to do: the new account's own synced skills arrive on sign-in, and the machine's hand-written skills (`~/.claude/skills/`, the project's `.claude/skills/`) are files and stay.

## What the project deliberately does not depend on

Worth stating, because each is a thing that usually has to be recreated and here does not:

- **No routine and no scheduled task.** grooph never had one. (This machine has one enabled routine, `Judge the nightly queue`, 07:00 daily — it belongs to `ars-magna` and touches nothing here. Leave it alone when handing grooph over, and if you ever recreate it on the new account, disable the old one first: two enabled routines on one repository judge the same work twice and collide on the same branch.)
- **No connector.** The session's connectors (Claude Docs, visualize, resmon, scheduled-tasks) are other projects' or general-purpose. grooph's agent surface is the `grooph` CLI and the `grooph-design` skill, both files in the clone.
- **No API key, no `.env`, no hosted service.** Decision 0001: static, local-first, no backend. grooph makes no model calls of its own.
- **No MCP server yet.** The MCP wrapper is a later stage; today an agent reaches grooph through the shell.

## The order to switch in

1. **Before signing out**, confirm the three brief sources are in the repository (`handoffs/briefs/`) and pushed. That is the only thing the old account holds that the new one cannot reach. It is done as of this file.
2. Sign in as the new account, in the same directory. Nothing needs moving.
3. Open a session in the clone and read [`AGENTS.md`](../AGENTS.md) → `docs/PROGRESS.md`. The project state, the plan, the last handback and the next handoff are all there.
4. Check that `grooph --version` still answers and `/grooph-design` is offered. If the clone has moved, re-run `scripts/install-local.sh` (it is idempotent and prints its plan first).
5. Only if you want the phone-readable briefs back: publish each file in `handoffs/briefs/` and record its new URL in that folder's table.

Nothing needs disabling, and no twin of anything can be created by accident.

## If it is ever another machine

The repository is the whole project, so a clone plus these three carries it:

- `~/.claude/projects/-Users-noir-Documents-grooph/` — the memory files and transcripts. Rename the folder to match the new path (dashes for slashes) if the clone lands somewhere else.
- `~/.claude/skills/` — the machine's hand-written skills, if you want the same ones.
- `gh auth login` for the GitHub side, and `scripts/install-local.sh` to put `grooph` and `/grooph-design` back on `PATH`.

Anything under `/private/tmp/claude-501/…` is a session scratchpad and is expected to vanish; nothing the project needs may live there. That rule is in `AGENTS.md` under Conventions, and this handover exists because three pages once did.
