| A-012 | 2026-09-30 | §11, A-007 | **Hook-written session events.** The file contract of A-007 gains a second file, written by the harness's hooks and not by the lead: one JSON line when a session or a subagent starts or stops (and, if asked, when a tool call finishes), appended to `.grooph/events/<session id>.jsonl`. | A-014 | 2026-10-01 | A-012 | **Sending the events, and reading a stale record honestly.** A-012's hook writes a session's events to a file in its own clone. (1) The events may be sent to a git branch that holds nothing else (`grooph events push`), and, **only when the owner of a project asks for it at install** (`--push`), a second hook does that at the end of every turn, in the background. That second hook keeps the same promises towards the session: it prints nothing, always exits 0, and returns nothing a harness reads. What it adds is a write outside the clone, to a branch that may hold only events: a branch with anything else on it is refused. (2) A record is only as fresh as its last line, so a reader does not call a session working when it has said nothing for half an hour: it says when the session was last seen. grooph still starts and supervises nothing. | The Operator session, after running the hook in a cloud lane (2026-10-01): a push is a snapshot, and a session cannot send what it writes as it stops, so a lane's last turn and its end never left the sandbox and the lane read "working" for good. Sending at each turn's end is the only way that line leaves; it uses the session's right to push, so it is asked for, not assumed. The reader's rule costs nothing and is right whether or not anything is sent. |
| A-015 | 2026-10-02 | A-014 | **A push that fails is on record, and an events branch names no person.** A-014 let a second hook send the events at a turn's end and promised it prints nothing and always exits 0. That promise stands; four things are added. (1) **Where the events go when no branch is checked out:** to one branch every such checkout shares (`grooph-events-detached`), so nothing is dropped for want of a name. (2) **A record of the push:** the push writes how it went into one small file beside the events (`.grooph/events/.last-push.json`): that it began, and then whether it arrived, on which try, or what git said. The file is never sent, is not an event, and is read by `grooph hooks status` and `grooph sessions`, never by a harness: the hook stays silent towards the session and stops being traceless. (3) **Sharing a branch:** many sessions may send to one events branch; a push that another session beat is made again on top of it for as long as its time allows, and a session whose file is on two branches is read as one session. (4) **An events commit is made as `grooph`,** not with the session's git identity: the branch holds ids, the names of agents and times, and nobody's name or e-mail address. | The Operator's trial of the turn-end push (2026-10-02): a cloud session starts with no branch checked out, the push threw for want of a name, and the hook swallowed it by design, so three turns were lost without a sign. | A-018 | 2026-10-04 | §5.1, §7.3 | **Subgroophs.** §5.1 says "A graph may contain subgraphs" and §7.3 "Group or nest subgraphs"; the graph document has had flat groups and no more. A group may now say where it came from (`from: "<template id>@<version>"`, with the slot values it was filled with in `with`, and a one-line `description`), and a group may hold groups. A group with a `from` is a **subgrooph**: a template placed inside a graph as a unit. It is drawn as one box that opens, named in the outline and in the lead's brief, and can be refreshed from a newer version of its template by a command that shows what would change and does not apply a change that loosens a brake (the list in A-008) unless the person asks for that change by name. **Nothing else moves.** A subgrooph's nodes, edges, loops and policies are ordinary members of the one document: the lead runs them as it runs any others, every rule applies to them as written, a stop inside one still ends the run, and a graph is still one session and its subagents. Nothing is resolved, fetched or inlined at compile time, so the document stays the whole truth and the same document still gives the same package. Groups form a tree: a group that holds itself is an error (`E_GROUP_CYCLE`), and a member of two groups, neither inside the other, is a warning (`W_GROUP_OVERLAP`). A graph has at most one lead, as it always said and never checked: a second is an error (`E_SECOND_LEAD`), because placing a template is the first operation that could add one. The change is additive within `grooph: 0`: every document that validates today validates afterwards, except a group that holds itself and a graph with two leads. Shape, rules, the alternative that was weighed (a node that refers to another graph, inlined by the compiler) and what follows (for-each, and intergroophs on the operation map, each its own amendment): decision 0025. | The owner asked for nested groophs under this name and said to draft them first (review desk, 2026-10-04). A long graph is hard to read on a phone, an agent composing a graph should place a proven template as a unit, and a placed unit should be able to take its template's fixes. By value, not by reference, because it adds no new way to loosen a brake and leaves the compiler, the validator's rules and share links as they are. |
| A-019 | 2026-10-05 | A-008 | **A check is a brake.** A-008 lists what a run may tighten and never loosen: gates, approvals, irreversible markers, budget and max-iteration stops, a bar's acceptance, critic isolation and the adaptation level. A check is not on it. A check node's own definition (its `check` field: its kind, what it runs, what counts as a pass, its threshold), every edge that leaves it, and its pass standing before what that led to, are now on that list. A lead may tighten them and may not loosen them; loosening one is a proposal for the human, as for every other brake. A program cannot tell a stricter command from a looser one, so at these doors, where a run's working copy or a template's newer version is taken into a graph: `grooph adopt`, a subgrooph's refresh, and the app's Adopt button, these are named and held until the person asks for that change by name: any change to a check's definition; its removal, or its becoming another kind of node, as for a gate or a critic; any change to an edge that leaves it, and any edge added there; except, on an edge that was already there, an approval newly asked, or evidence added to what the edge hands a critic with none taken away; and a new way to what its pass led to that does not pass it, as for a critic's verdict; and a stop that halts, made to end in success (its outcome set so, or taken away), wherever it stands, since a failing verdict that led there would then end the run well.
