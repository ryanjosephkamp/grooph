# The clean profile for the Claude Code run

How the session is started so that it loads nothing of the account's and can touch nothing but its own folder ([`../PROTOCOL.md`](../PROTOCOL.md) §2). It is three things: a configuration folder of its own (`make-profile.sh`), one settings file in it (`profile/settings.json`), and the command that starts the session (`start-claude.sh`).

**Nothing here has been run with a model.** Each line below says where it comes from: **documented** (Claude Code's documentation at code.claude.com/docs, read on 2026-10-04 for version 2.1.289; the page is named), **seen** (the installed `claude` printed it, with no session started), or **not known until the rehearsal**. The rehearsal is where the last kind is found out.

It runs in a terminal and not in the desktop app: the app's sessions are given tools that read other sessions.

## The folder

| Line | What it is for | How it is known |
|---|---|---|
| `CLAUDE_CONFIG_DIR=~/grooph-game/profile-claude` | Settings, sign-in, session history, plugins, skills, agents and memory are read from this folder and not from `~/.claude`. It is new and holds only `settings.json`, so the account's instructions (`~/.claude/CLAUDE.md`), skills, agents, plugins and servers are not there to load | documented (`env-vars`: "Override the configuration directory … All settings, session history, and plugins are stored under this path"; `authentication`: each directory "has its own settings, session history, and claude.ai login") |
| a sign-in of its own | The sign-in is kept in the macOS Keychain under an entry keyed to this folder, so the owner signs in to it once | documented (`authentication`); seen: `claude doctor` under this folder says "Not signed in to claude.ai", and writes its `.claude.json` inside the folder |
| no instructions above the folder | A session reads `CLAUDE.md` from the folders above its own. `start-claude.sh` refuses to start if one is there; today none is (`~/CLAUDE.md`, `~/grooph-game/CLAUDE.md`) | documented (`memory`); the check is the script's |
| no managed settings | `/Library/Application Support/ClaudeCode` would be loaded by every session. It does not exist on this Mac; `start-claude.sh` refuses to start if it appears | seen |

## The settings file

| Line | What it is for | How it is known |
|---|---|---|
| `permissions.defaultMode: "dontAsk"` (and `--permission-mode dontAsk`) | Nothing ever asks. A call that would have prompted is refused, and the session is told. A session that stops at minute three to ask is six hours lost; one that is refused loses a turn | documented (`permission-modes`: "auto-denies every tool call that would otherwise prompt you. Claude still runs actions that need no approval … plus actions matching your `permissions.allow` rules") |
| `permissions.blockReadsOutsideWorkingDirectories: true` | The file tools (Read, Grep, Glob) refuse any path outside the session's folder, in every mode. With the sandbox on, commands lose `/Users` and the other roots that hold a person's files, except the session's folder, its temp folder and the git configuration | documented (`settings-reference`) |
| `permissions.deny: WebFetch, WebSearch` | The two tools that reach the web are taken away | documented (`permissions`: a bare tool name in `deny` removes the tool) |
| `permissions.deny: AskUserQuestion` | In this mode Claude Code refuses its own question tool every time it is called. The lead's brief says to ask at a gate "with `AskUserQuestion` when it is available, otherwise in plain text": with the tool taken away it asks in plain text at once, which the owner answers by typing. (Codex has no such tool, so both runs ask the same way) | documented (`permission-modes`: dontAsk "also denies the built-in `AskUserQuestion` tool even if your allow rules match it") |
| subagents | A subagent the lead starts runs in the same mode and under the same rules and sandbox, since the package's agents name no mode of their own | documented (`sub-agents`: "If you leave it unset, the subagent inherits the main conversation's permission mode"; `sandboxing`: subagents "use the same sandbox configuration") |
| `permissions.deny: Bash(git push), Bash(git push *)` | `git` may do anything but push. (It could not anyway: github.com is not a host the sandbox allows) | documented (`sandboxing`: "Explicit deny rules are always respected" for sandboxed commands) |
| `sandbox.enabled: true`, `failIfUnavailable: true` | Every shell command, and what it starts, runs inside a boundary the operating system enforces (Seatbelt on macOS). If the sandbox cannot start, Claude Code does not start | documented (`sandboxing`) |
| `sandbox.autoAllowBashIfSandboxed: true` | A command that runs inside the sandbox needs no permission, in any mode. This is what lets `npm`, `node`, `git` and the browser run with nobody there | documented (`sandboxing`, "Auto-allow mode … works independently of your permission mode setting") |
| `sandbox.allowUnsandboxedCommands: false` | A command that fails inside the sandbox cannot be tried again outside it | documented (`sandboxing`, "strict sandbox mode") |
| writes | A command may write in the session's folder and its own temp folder, and nowhere else; inside its folder it may not write `.claude/` or `.git/config` and `.git/hooks` | documented (`sandboxing`, "Protected paths") |
| `sandbox.filesystem.allowWrite` and `allowRead`: `~/grooph-game/npm-cache-claude` | npm must write its cache somewhere, and its usual place is under `/Users`, which is closed. This folder is new and empty, and is the only place outside its own a session can write | documented that `npm` needs this (`sandboxing`); that this folder suffices is **not known until the rehearsal** |
| `sandbox.filesystem.allowRead`: `~/Library/Caches/ms-playwright` | Where Playwright keeps the browser it drives, installed before the clock starts | documented that `allowRead` in user settings re-opens a path under the block; that Chromium then starts is **not known until the rehearsal** |
| `sandbox.network.allowedDomains: ["registry.npmjs.org"]`, `strictAllowlist: true` | A command reaches the npm registry and no other host; any other is refused, not asked about | documented (`sandboxing`, "Network isolation") |
| `sandbox.network.allowLocalBinding: true` | The game's dev server may listen on this machine and the critic's browser may open it | documented (`sandboxing`, "A command fails to reach a server on localhost") |
| `sandbox.network.allowMachLookup: ["*"]` | macOS programs find the system's services by name, and a browser needs some. The documentation says Playwright needs its services listed and does not say which, so all are allowed for the rehearsal. What stays closed: Apple Events, so `open` and `osascript` fail (they need `allowAppleEvents`, which is not set). What this may open is not established: the services that answer by name include Spotlight's (`mdfind` would list file names anywhere on the disk), the Keychain's, the clipboard's and launchd's. The commands that reach them are refused by name (next row), which is a speed bump and not a wall, and `record.sh` counts any use | the key is documented (`settings-reference`: "`\"*\"` alone matches every service"; `allowAppleEvents` for `open` and `osascript`); that `"*"` is needed, or enough, and what it opens, are **not known until the rehearsal** |
| `permissions.deny: Bash(mdfind *)`, `mdls`, `security`, `launchctl`, `osascript`, `open`, `pbpaste`, `screencapture` | The commands that would use those services, refused when called by name. A command can still be reached another way (`node` can start anything), so this is not the boundary; the sandbox is | documented (`permissions`: "Bash rule limits"; `sandboxing`: explicit deny rules are respected for sandboxed commands) |
| `env.npm_config_cache`, `npm_config_userconfig` | npm's cache and its own settings file are in the folder above, so npm does not look under `/Users` | npm's documented variables; **not known until the rehearsal** under the sandbox |
| `autoMemoryEnabled: false` (and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`) | Claude Code neither reads nor writes its own memory of earlier sessions | documented (`settings-reference`, `env-vars`) |
| `disableClaudeAiConnectors: true` (and `ENABLE_CLAUDEAI_MCP_SERVERS=false`) | The servers connected to the account on claude.ai are neither fetched nor connected | documented (`settings-reference`, `env-vars`) |
| `cleanupPeriodDays: 3650` | The transcript is not deleted after thirty days | documented (`settings-reference`) |
| `sandbox.filesystem.denyRead`: `/tmp`, `/private/tmp`, and this account's temp folder under `/var/folders` | **The checks were readable without this.** The read block above closes `/Users`; it does not close `/tmp`, and Claude Code keeps every session's scratch files and subagent transcripts in `/tmp/claude-<uid>/`, one folder for all the sessions on the machine. On 2026-10-04 that folder held whole copies of `acceptance/check.mjs`, `prove.mjs` and the proof outputs, left by the sessions that wrote and reviewed them. The account's own temp folder (`getconf DARWIN_USER_TEMP_DIR`) is closed for the same reason: other lanes write there while a run is open. Only its `T` folder is named, not all of `/var/folders`, whose cache folders a browser may need | documented (`settings-reference`: `denyRead`, and "Sandboxed commands under the block" for the roots the block covers, which do not include `/tmp`; `claude-directory` for where scratch files are kept); that the browser and `git` still work with these closed is **not known until the rehearsal**. If the browser does not start, the `/var/folders` entry is the first thing to try without, on the driver's word |
| `sandbox.filesystem.denyWrite`: `<game home>/rehearsal-claude/.grooph/hooks`, `<game home>/grooph-game-experiment-claude/.grooph/hooks` | **The wall around the hook.** No command, whatever it is or starts, can write the hook's two files, though they are inside the session's own folder. The hook is run by Claude Code outside the sandbox with the owner's access, so a session that could rewrite it could leave the sandbox. `record.sh` compares both files with the first commit after every session all the same | documented (`settings-reference`, `sandbox.filesystem.denyWrite`: "Block sandboxed commands from writing to specific paths, including paths inside a directory that is otherwise writable"); that it holds is **not known until the rehearsal**, and the comparison afterwards does not depend on it |
| `permissions.deny: ListAgents, SendMessage`; `crossSessionInbound: "refuse"`; `disableRemoteControl: true` | A terminal session can otherwise list the other Claude Code sessions on this machine, with their names and folders, and write to them, and they to it: the lanes that built this experiment among them. Denied both ways. `SendMessage` is also how a lead goes on with a subagent it started earlier, so that is gone too: the lead dispatches afresh each time, which is what the graph's edges say (nothing in the package names either tool) | documented (`cross-session-messaging`, "Turn off cross-session messaging"; `settings-reference`) |
| `syncClaudeAiSkills: false`, `syncClaudeAiPlugins: false` | A session signed in with a claude.ai subscription downloads the skills and plugins of that account into its configuration folder. Not here | documented (`settings-reference`; `skills`, "Where synced skills load") |
| `enableArtifact: false` | No tool that publishes a page on claude.ai | documented (`settings-reference`) |
| `respondToBashCommands: false` | A line the owner types with `!` at the sign-in is run and not answered by the model: without this, checking the path would be a model call nobody recorded | documented (`interactive-mode`, "Shell mode with `!` prefix") |

## The command

| Line | What it is for | How it is known |
|---|---|---|
| `env -i` with `HOME`, `USER`, `TERM`, `LANG` | Nothing of the terminal's own environment reaches the session: no key, no proxy, no `GROOPH_MODELS` | a shell's own |
| `PATH=/opt/homebrew/bin:/Library/Developer/CommandLineTools/usr/bin:/usr/bin:/bin:/usr/sbin:/sbin` | `node`, `npm` and `git` are on it. The developer tools' own folder comes before `/usr/bin`, whose `git` is a shim that keeps a cache in the account's temp folder, now closed to commands: it would print two `error:` lines at every call (seen with a stand-in sandbox, not Claude Code's; `xcrun -f git` names the real one). `~/.local/bin`, where the `grooph` command is a link into the clone that holds the checks, is not. `start-claude.sh` looks for `grooph` on this very path and refuses to start if it is found | seen (`command -v` on this Mac) |
| `ZDOTDIR=<profile>/no-shell-startup` | The shell a command runs in reads its start-up files from this empty folder and not from the account's, which could put `~/.local/bin` back on the path | zsh's own; that Claude Code's shell honors it is **not known until the sign-in**, where the runbook has the owner type `!command -v grooph`. A line typed with `!` runs outside the sandbox (documented, `sandboxing`: "Commands you type yourself"), so it shows the shell's path and nothing about the sandbox's walls: those are first met in the rehearsal |
| `claude` by its full path | The harness is in `~/.local/bin` too, so it is named whole | seen |
| `--model claude-opus-5-5` | The lead is the session, on the tier the owner answered is Opus 5.5 | documented (`cli-reference`: "an alias … or a model's full name") |
| `--allowedTools "Edit(/**)"` | The session may create and change files in its own folder without asking. On the command line a rule's leading `/` is the session's folder | documented (`permissions`, "Read and Edit": "CLI flags or session rules: `<primary working directory>/path`") |
| `--strict-mcp-config`, with no `--mcp-config` | No MCP server at all, whatever any file says | documented (`cli-reference`, `mcp`) |
| `--setting-sources user,project` | The profile's settings and the repository's own (the event hook) are read; a `.claude/settings.local.json` is not | documented (`cli-reference`) |
| `--no-chrome` | No connection to a browser extension | documented (`cli-reference`) |
| `--session-id <a new one>` | The session's id is chosen before it starts, so the record names it and its transcript beforehand | documented (`cli-reference`; `sessions` for where the transcript is) |
| `DISABLE_AUTOUPDATER=1` | Claude Code does not replace itself in the middle of six hours | documented (`env-vars`) |
| `CLAUDE_CODE_TMPDIR=~/grooph-game/t`, and `TMPDIR` the same | Claude Code keeps this session's temp files, and gives its commands a temp folder, under a folder that is the profile's alone and not under `/tmp`, which is closed (above). The name is short on purpose | documented (`env-vars`: "Override the temp directory used for internal temp files. Claude Code appends `/claude-{uid}/`"; the same row says commands get "a short fallback `$TMPDIR` under the system default when your override is a long path", and does not say how long is long: **not known until the rehearsal**, where a command that cannot use its temp folder is refused and `record.sh` shows it) |
| `CLAUDE_CODE_DISABLE_OFFICIAL_MARKETPLACE_AUTOINSTALL=1` | The first launch in a new configuration folder does not register the plugin marketplace, so the profile gets no `plugins` list of its own making | documented (`env-vars`) |
| `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK=1` | A request a safety classifier flags is not moved to another model: every reply is from the model the record names, or there is none | documented (`env-vars`; `model-config`, "Automatic model fallback") |
| `CLAUDE_CODE_AUTO_CONNECT_IDE=false` | No connection to an editor | documented (`env-vars`) |
| `--disallowedTools "Edit(//<the session's folder>/.grooph/hooks/**)"` | The hook's two files are the one thing in the session's folder that Claude Code runs outside the sandbox, with the owner's access, and they are not among the paths Claude Code protects by itself. This rule refuses the file tools, and the commands Claude Code can see are writing a file (`cat`, `sed`, `tee`, a redirection). It does not stop a script that opens the file itself, so it is not the wall: the `denyWrite` line in the settings is | documented (`permissions`, "Read and Edit": the rules "don't apply … to arbitrary subprocesses that read or write files indirectly, like a Python or Node script that opens files itself. For OS-level enforcement … enable the sandbox") |

## What still loads, and is the harness's own

Claude Code's built-in tools, its built-in skills and commands, and the trailer it adds to a commit it makes. They are the same for any session of this version, and they are part of what "run in Claude Code" means. The repository's own package loads, as it should: five agents, one skill, and the event hook, which runs outside the sandbox with the owner's access, as every hook does, and writes one line to `.grooph/events/`.

Claude Code itself talks to Anthropic, outside the sandbox: "reach the npm registry and nothing else" is true of what the session runs, not of the harness.

## What a session cannot do that its brief says it may

**Change one of its own agent files.** The lead's brief says that when it amends the graph in a way that changes a node's tools, it should also edit that node's file under `.claude/agents/`; and `MAPPING.md` says a node's model is changed in that file. Claude Code never lets a session write under `.claude/` without a person's yes, in any mode but the one that skips every check, and an allow rule does not change that (documented: `permission-modes`, "Protected paths": in `dontAsk`, "Denied"; and the sandbox denies the same paths to commands). So here such an edit is refused, the lead is told, and the run goes on with the agent file as compiled.

What is left to an adaptive lead: it can amend its working copy of the graph and note it, as its brief says; it can name a model when it dispatches a node, which Claude Code honors over the agent file (documented: `env-vars`, the row for `CLAUDE_CODE_SUBAGENT_MODEL`); it cannot widen or narrow a node's tools. In an everyday session the same edit would stop and wait for a person, which in a run nobody watches is worse than a refusal. Whether Codex lets a lead edit its own agent files is not known; if it does, this is a difference between the two runs, and it is written here before either.

## What a session can still do that the protocol would rather it could not

- **Read system files with a command**: `/opt/homebrew`, `/usr`, `/Library`, `/var/folders` except this account's temp folder. The checks are under `/Users`, which is closed to commands and to the file tools both, and the temp folders where other sessions keep copies of them are closed to commands (above).
- **Reach any port on this machine's `localhost`** (`allowLocalBinding`): the key is a yes or a no, with no list of ports, so a session's own dev server cannot be told from another program's. `start-claude.sh` writes the ports that were open into the record, and refuses to start while port 4361, where the checks are served, is open or anything of the checks' folder is running. Nothing stops another session from opening one later: while a rehearsal or the run is open, no lane runs or serves the checks (`PROTOCOL.md` section 10).
- **Look up any system service** (`allowMachLookup: ["*"]`): see that row. It is the loosest line here and the first to narrow once the rehearsal shows what the browser asks for.
- **Run any command, not only `npm`, `node` and `git`**, inside the sandbox (`autoAllowBashIfSandboxed`). The protocol's list of commands is not what bounds a session; the sandbox is (`PROTOCOL.md` section 10 says why).

## What could not be made the same as it will be for Codex, as far as can be known now

- **The terms.** Codex has its own words for a sandbox, an approval policy and a profile. The intent above (own folder, npm registry only, no push, nothing asks, nothing of the account's) will be said in those words, and where one cannot be said the difference is written down before that run.
- **`localhost` and system services.** Whether Codex's sandbox can be opened exactly this far and no further for a dev server and a browser is not known.
- **Refuse or ask.** Here a call outside the rules is refused and the session goes on. If Codex can only ask or stop, a session there could wait where this one would not.
- **The hook.** Claude Code runs the repository's hook once the folder is trusted. Codex runs a hook only after it has been reviewed in `/hooks` (`grooph hooks install` says so), which is one more step before its clock.
- **The models and the date**, as `PROTOCOL.md` §5, §6 and §10 say.
